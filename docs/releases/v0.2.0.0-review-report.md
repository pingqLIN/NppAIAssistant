## 4. Findings and Corrections

### F1 — Feature branch was not a valid release baseline

Severity: **BLOCKER**

The feature branch is ahead 6 / behind 2 relative to `main`. Tagging it directly would omit main history and bypass semantic conflict review.

**Correction:** created `release/v0.2.0.0-prep` from `main`; R1 requires isolated semantic integration of the feature branch.

### F2 — Two independent Release ZIP producers

Severity: **HIGH**

The pre-existing CI tag path created a ZIP with `7z`, while `scripts/package-npp-ai-plugin.ps1` created a separate package. Two independently compressed archives can have different bytes, layout, and SHA-256 even when they contain the same DLL.

**Correction:** ordinary `CI_build.yml` no longer publishes GitHub Releases. `release.yml` is the single canonical x64 package/release path and calls `package-npp-ai-plugin.ps1` once.

### F3 — Release asset integrity needed pre- and post-publication verification

Severity: **HIGH**

Publishing first and only then checking the public asset would expose an incorrect asset before integrity verification.

**Correction:** the release job now:

1. transfers the canonical ZIP as a workflow artifact;
2. verifies SHA-256 before GitHub upload;
3. creates a **draft** Release from an already-existing tag;
4. downloads the draft asset via GitHub CLI and verifies SHA-256;
5. publishes only the verified draft;
6. downloads the final public ZIP and verifies SHA-256 again.

If draft verification fails, the workflow fails while the Release remains draft for investigation.

### F4 — Third-party Action held the release write boundary

Severity: **HIGH (supply-chain hardening)**

A third-party release Action originally held `contents: write` in the new design.

**Correction:** removed the third-party Release action. The publish job uses GitHub CLI (`gh`) supplied by GitHub-hosted runners with `GH_TOKEN`, and `gh release create --verify-tag` requires the tag to exist before release creation.

### F5 — `workflow_dispatch` input crossed directly into PowerShell source

Severity: **HIGH**

The initial draft embedded `${{ inputs.version }}` directly inside a PowerShell `run:` script and validated it only after interpolation. This creates an expression-to-shell injection boundary.

**Correction:** the input is now passed through the step environment (`REQUESTED_VERSION`) and then regex-validated as exactly four numeric version components.

### F6 — RC schema validation and final repository URL were conflated

Severity: **MEDIUM**

A pull-request or manual RC does not yet have a final public Release ZIP URL, so requiring a direct ZIP during schema-only validation would create false negatives.

**Correction:** `scripts/validate-npp-plugin-entry.ps1` separates:

- official schema validation; and
- final `-RequireDirectHttpsZip` policy.

Tag release runs enable the final direct-HTTPS-ZIP requirement and later perform an actual public download.

### F7 — Plugins Admin author metadata drift

Severity: **MEDIUM**

The prior PR template used `NppAIAssistant Contributors`, while project metadata and the existing published entry use `pingqLIN`.

**Correction:** release-facing Plugins Admin draft material now consistently uses `pingqLIN`.

### F8 — Worktree branch mapping was ambiguous

Severity: **MEDIUM**

An earlier plan draft used a local `-prep-local` branch while later push commands targeted `release/v0.2.0.0-prep` without an explicit refspec.

**Correction:** SOP and release plan now use a local tracking branch with the exact remote branch name. Temporary branches must push explicitly with `HEAD:release/v0.2.0.0-prep`.

### F9 — Release workflow needed a PR-exercisable path

Severity: **MEDIUM**

A tag-only release workflow can remain syntactically and behaviorally untested until the first real release.

**Correction:** `release.yml` now has a path-filtered `pull_request` path that reads the version from `src/NppAIAssistantVersion.h`, builds x64, creates the canonical package, validates layout/schema/hash, and uploads the artifact. The publish job remains tag-only.

### F10 — Current Actions jobs fail before runner startup

Severity: **EXTERNAL BLOCKER**

Diagnostic evidence on release-prep head `0e872841c99ee9303940db2192bb3490c15e355f`:

- CI_build run `32625234394`: all six matrix jobs concluded `failure` with `steps=[]`.
- Release run `32625234423`: package job concluded `failure` with `steps=[]`; publish job was skipped as expected for PR context.
- job log download returns `BlobNotFound`, consistent with no runner log being produced.
- both runs completed within only a few seconds.

Historical comparison:

- PR #3 run `30595269739` did start runners and execute steps.
- x64 Release, x64 Debug, Win32 Release and Win32 Debug succeeded in that historical run.
- ARM64 Release/Debug failed at the actual `MSBuild of plugin dll` step.

The current failure therefore cannot be classified as a C++ compilation regression from available evidence. It occurs before runner execution and must be investigated at repository/account Actions admission, policy, or infrastructure level.

Changing `checkout@v7` back to the repository-known `checkout@v6` and removing the extra `setup-python` Action did not change the pre-run failure, which further reduces confidence that a specific workflow step is the root cause.
